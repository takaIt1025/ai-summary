# iOSアプリ ヒット予測スキル

完全無料のAPI/ツールのみを使用して、アプリアイデアのヒット可能性を定量スコアで評価します。
「作るべきか？」を判断するための Go/No-Go 判定を出します。

## プロンプト

```
あなたは個人開発アプリのビジネス評価専門家です。
以下のアプリアイデア（キーワード）について、ヒット可能性を5軸で定量評価してください。

【評価対象】: $ARGUMENTS

【評価方針】
- 対象プラットフォーム: iOS（App Store）日本市場
- 対象開発者: 個人開発者（1人、予算・時間に制約あり）
- 使用ツール: 完全無料のAPI/エンドポイントのみ
- 出力言語: 日本語
- 最終判定: 25点満点スコア → Go / Conditional Go / No-Go の3段階
- **複数のアイデアが渡された場合は、各アイデアを個別にStep1〜8で評価したうえで、必ず最後に「横断比較・優先順位」セクションを設けること**

---

【作業手順】

### Step 1: 調査キーワードの整理

入力されたアプリアイデアから、以下を特定する:
- **コアキーワード**: App Storeで検索されるであろうメインワード（2〜3個）
- **ユーザー像**: 誰がこのアプリを使うか（一言で）
- **解決する問題**: どんな不便・欲求を解消するか

---

### Step 2: 軸①「需要トレンド」を測る（1〜5点）

Google Trendsの代替として、Google Suggestの**接尾辞展開**で需要の強さを推定する。

以下の接尾辞でSuggestを取得し、サジェスト出現数と質を評価する:
- "アプリ" / "無料" / "おすすめ" / "iphone"
- "使い方" / "とは" / "人気"
- ユーザー像に合った語（例: 初心者なら「初心者」「始め方」）

```bash
curl -s "https://suggestqueries.google.com/complete/search?client=firefox&hl=ja&q=<URLエンコード済みキーワード><接尾辞>" | python3 -c "
import sys, json
raw = sys.stdin.buffer.read()
for enc in ['utf-8', 'cp932', 'shift_jis', 'euc-jp']:
    try:
        data = json.loads(raw.decode(enc))
        print(len(data[1]), data[1])
        break
    except:
        continue
"
```

**採点基準（需要トレンド）**:
| スコア | 基準 |
|---|---|
| 5点 | サジェスト5件以上 × 複数接尾辞で出現 × 「アプリ」「無料」が上位 |
| 4点 | サジェスト3件以上 × 「アプリ」系が出現 |
| 3点 | サジェスト1〜2件 または 関連語のみ |
| 2点 | サジェストがほぼ出ない（ニッチすぎ or 認知低い） |
| 1点 | サジェスト0件（需要が確認できない） |

---

### Step 3: 軸②「競合の隙間」を測る（1〜5点）

iTunes Search APIで競合アプリTOP20を取得し、「満足していないユーザーがいるか」を評価する。

```bash
curl -s "https://itunes.apple.com/search?term=<URLエンコード済みキーワード>&country=jp&entity=software&limit=20&lang=ja_jp" | python3 -c "
import sys, json
data = json.load(sys.stdin)
print(f'Total: {data[\"resultCount\"]}')
for i, app in enumerate(data['results'][:10]):
    updated = app.get('currentVersionReleaseDate','')[:10]
    print(f'{i+1}. {app.get(\"trackName\")} | ★{app.get(\"averageUserRating\",0):.2f} ({app.get(\"userRatingCount\",0):,}件) | {app.get(\"formattedPrice\")} | 更新:{updated}')
"
```

隙間の指標:
- 上位アプリに評価3.5以下のものが多い → 不満が多い
- 直近2年以上更新停止のアプリが上位に残っている → 放置されている
- 検索ヒット数が少ない（< 10件）→ 競合が薄い
- 上位アプリがすべて大企業・外資 → 日本語品質で差別化の余地あり

**採点基準（競合の隙間）**:
| スコア | 基準 |
|---|---|
| 5点 | 強敵（レビュー1万超）が0 × 評価3.5以下の不満アプリが上位にいる |
| 4点 | 強敵1〜2個 × 更新停止アプリが上位にある or 評価が低い競合がいる |
| 3点 | 強敵2〜3個 × 一部に隙あり（外資ばかり、日本語品質が低い等） |
| 2点 | 強敵4個以上 × 全体的に高評価でアクティブ更新中 |
| 1点 | 超強敵（レビュー5万超）が複数 × 隙が見当たらない |

---

### Step 4: 軸③「収益ポテンシャル」を測る（1〜5点）

同じItunes Search APIの結果から、マネタイズ環境を評価する。

確認項目:
- 有料アプリの存在（price > 0）
- 「サブスク」「プレミアム」「Pro」などの語が説明文に含まれるか
- 上位アプリの価格帯（¥120〜¥600、¥980以上のサブスク等）

```bash
# 価格帯とサブスク有無を確認
curl -s "https://itunes.apple.com/search?term=<キーワード>&country=jp&entity=software&limit=20&lang=ja_jp" | python3 -c "
import sys, json
data = json.load(sys.stdin)
paid = [(a['trackName'], a['formattedPrice']) for a in data['results'] if a.get('price',0) > 0]
print('有料アプリ:', paid[:5])
sub_count = sum(1 for a in data['results'] if any(w in a.get('description','') for w in ['サブスク','定期購読','月額','年額','Premium','Pro','プレミアム']))
print('サブスク系:', sub_count, '件')
"
```

**採点基準（収益ポテンシャル）**:
| スコア | 基準 |
|---|---|
| 5点 | 有料アプリ3件以上 × サブスク系アプリが複数存在 |
| 4点 | 有料アプリ1〜2件 または サブスク系が1〜2件 |
| 3点 | 全部無料だがIAP（アプリ内課金）の記載あり |
| 2点 | 全部完全無料 × IAP記載なし（マネタイズが難しい市場） |
| 1点 | 無料ゲーム/広告モデルのみ（個人開発での収益化は困難） |

---

### Step 5: 軸④「個人開発フィージビリティ」を測る（1〜5点）

競合アプリの説明文・機能から、1人で作れる難易度を推定する。

難易度を上げる要因:
- リアルタイム通信・マルチプレイヤー機能
- 大規模データベース・コンテンツ運用が必要
- 外部API依存（有料、レート制限あり）
- 位置情報・カメラ・ハードウェア連携の複雑さ
- 医療・金融など規制領域

個人開発に向く要因:
- ローカル完結（オフラインで動く）
- ユーザー生成コンテンツ型（ユーザーが中身を作る）
- ツール・計算系（ロジックが明確）
- 学習・習慣系（シンプルなデータ管理）

```bash
# 上位3アプリの説明文を確認して機能複雑度を推定
curl -s "https://itunes.apple.com/search?term=<キーワード>&country=jp&entity=software&limit=5&lang=ja_jp" | python3 -c "
import sys, json
data = json.load(sys.stdin)
for app in data['results'][:3]:
    print(f'=== {app[\"trackName\"]} ===')
    print(app.get('description','')[:400])
    print()
"
```

**採点基準（個人開発フィージビリティ）**:
| スコア | 基準 |
|---|---|
| 5点 | ローカル完結 × ロジック明確 × 外部依存なし（ツール/計算/記録系） |
| 4点 | 軽いAPI連携あり × リアルタイム不要 × 1〜2ヶ月で MVP可能 |
| 3点 | バックエンド必要だが小規模 × Supabase等で対応可能レベル |
| 2点 | リアルタイム通信 or 大規模コンテンツ管理が必要 |
| 1点 | チーム開発前提 / 規制対応 / 大規模インフラ必須 |

---

### Step 6: 軸⑤「拡散・発見しやすさ」を測る（1〜5点）

SNSやロコミで広がりやすいかを、Google Suggestのシグナルで推定する。

確認項目:
- Suggestに「インフルエンサー名 + キーワード」が出るか
  （例: 「ポーカー ヨコサワ」「マンダラチャート 大谷」）
- 「シェア」「友達」「一緒に」系のサジェストが出るか
- 競合アプリの説明文に「SNSシェア」「友達招待」機能があるか
- カテゴリ的にSNSで映えるか（ビジュアル系・成果共有系）

```bash
for suffix in "インフルエンサー名" "シェア" "友達" "みんな" "話題"; do
  curl -s "https://suggestqueries.google.com/complete/search?client=firefox&hl=ja&q=<キーワード>$suffix" | python3 -c "..."
done
```

**採点基準（拡散・発見しやすさ）**:
| スコア | 基準 |
|---|---|
| 5点 | インフルエンサー言及あり × 成果共有UIが自然に生まれる × SNS映え |
| 4点 | SNS拡散の素地あり（友達招待 or 共有機能が競合に存在） |
| 3点 | 口コミ広がりは期待できるが、SNS拡散は弱い |
| 2点 | プライベート用途（日記・家計等）× 共有しにくい性質 |
| 1点 | ニッチすぎてSNSでの認知拡大が難しい |

---

### Step 7: 総合スコアと Go/No-Go 判定

各軸のスコアを合計し、判定する。

```
総合スコア = ①需要トレンド + ②競合の隙間 + ③収益ポテンシャル + ④フィージビリティ + ⑤拡散性
```

**判定基準**:
| 総合スコア | 判定 | 意味 |
|---|---|---|
| 20〜25点 | 🟢 **Go** | 今すぐ作れ。市場・実現性・収益性がそろっている |
| 14〜19点 | 🟡 **Conditional Go** | 条件付きGo。弱い軸を補う戦略を立てて着手 |
| 8〜13点 | 🔴 **No-Go（要再設計）** | アイデアを軸ごとに再設計してから再評価 |
| 〜7点 | ⛔ **No-Go** | このアイデアは見送り。別のアイデアへ |

**軸別の解釈**:
- ①が低い → 需要自体が存在しない可能性。ピボットか市場開拓が必要
- ②が低い → 競合が強すぎる。ニッチへの絞り込みを検討
- ③が低い → 収益化が難しい市場。広告モデルや別アイデアを検討
- ④が低い → 1人では作れない規模。スコープを絞る
- ⑤が低い → 自然な拡散が期待できない。ASO・有料UAへの依存度が上がる

---

### Step 7.5: マネタイズ戦略と収益シミュレーション

**全判定で必ず実施する。Conditional Go の場合は特に詳細に記述する。**

#### A. 推奨マネタイズモデルの選定

Step 4で収集した競合の価格・サブスク状況をもとに、以下の観点で最適モデルを選定する:

| モデル | 向いているケース |
|---|---|
| 無料 + 買い切りIAP | 機能制限を解除する一回払い。ツール系・記録系に向く |
| 無料 + サブスク | 継続的な価値提供（AI機能・クラウド同期等）がある場合 |
| 有料アプリ（買い切り） | 競合がほぼ無料の中で"質の差"を打ち出したい場合 |
| 広告モデル | 無料で広げたい × DAUを確保できる × 他モデルが難しい場合 |
| フリーミアム（上限解除） | 記録数・項目数の上限を無料で制限する（ゲムコレ方式） |

競合の採用モデルと価格帯を参考に、推奨モデルと価格を1つ決定する。

#### B. 市場規模の逆算と収益シミュレーション

```python
# ── 市場規模の推定 ──
# 競合レビュー数 ÷ レビュー率(1%) = 推定市場DL数
# 競合が極端に少ない場合は隣接市場（類似カテゴリの強い競合）で補正する

competitor_total_reviews = N   # Step 3で取得したTOP3合計レビュー数
estimated_market_dl = competitor_total_reviews / 0.01

# ── 自社シェア想定 ──
# 競合の強さ（Step 3スコア）に応じて設定
# ★★以下（スコア5点）: 悲観20% / 標準35% / 楽観50%
# ★★★（スコア3〜4点）: 悲観10% / 標準20% / 楽観30%
# ★★★★以上（スコア1〜2点）: 悲観3% / 標準8% / 楽観15%

# ── モデル別月次収益計算 ──
# [買い切りIAP]
#   月次DL = 年間推定DL × シェア ÷ 12
#   月次収益 = 月次DL × IAP転換率(2〜5%) × 価格
#
# [サブスク]
#   累積ユーザー = 推定DL × シェア
#   MRR = 累積ユーザー × 課金転換率(3〜8%) × 月額
#
# [広告]
#   月間DAU = 月次DL × 継続率(20〜40%)
#   月次収益 = 月間DAU × 表示回数/日(3) × eCPM(¥100〜200) ÷ 1000
```

3ケース（悲観・標準・楽観）を計算し、**標準ケースの月次収益・年次収益**を主要指標として出力する。

#### C. 収益化ロードマップ

- **リリース〜3ヶ月（認知獲得期）**: 無料で広げる戦略 → レビュー獲得 → ASO改善
- **4〜12ヶ月（収益化期）**: IAP/サブスクの訴求強化 → アップデートでリテンション
- **1年以降（成長期）**: 機能拡充 or 隣接市場への展開

### Step 8: 個人開発者向け「次の一手」提案

判定結果とStep 7.5のマネタイズ戦略をもとに、具体的なアクションを提示する。

- 🟢 Go の場合: MVP（最小機能）の定義 + 推奨マネタイズモデルの実装方針
- 🟡 Conditional Go の場合: 弱い軸を改善する方向転換案（2〜3案）+ 収益を上げるための条件
- 🔴 No-Go の場合: このアイデアの「どこを変えたらGoになるか」を1〜2個提示

## 技術的制約と注意

- 検索ボリュームの**正確な数値**は無料では取得不可。Suggestの出現パターンで**相対評価**する
- Google Suggestは非公式エンドポイント。Shift-JIS/UTF-8両対応のデコード処理を必ず入れる
